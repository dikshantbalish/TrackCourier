# TrackCourier

TrackCourier is a shipment-tracking website with a public tracking page and a
password-protected admin interface for managing shipments. The application is
built with FastAPI, serves its HTML/CSS/JavaScript frontend from the same
service, and stores admin accounts, shipments, and tracking events in a
relational database.

This README covers the project structure, local development, configuration,
API, tests, production deployment, custom domains, and operational
considerations. The longer [deployment guide](docs/deployment.md) contains
additional host-specific notes.

## Features

- Public shipment tracking by tracking ID.
- Admin login using a signed, HTTP-only session cookie.
- Admin operations to create, list, view, update, delete shipments, and add
  tracking events.
- Tracking history associated with each shipment.
- Static frontend assets served by the FastAPI application.
- PostgreSQL support through SQLAlchemy and Psycopg.
- Interactive command-line setup for creating the initial admin account.
- API documentation generated by FastAPI at `/docs`.

served from the same origin.

## Requirements

- Python 3.13 (the version selected by `.python-version`; the package declares
  support for Python 3.11 or newer).
- [`uv`](https://docs.astral.sh/uv/) for creating the environment and syncing
  the locked dependencies.
- PostgreSQL for local use with real persistent data and for production.
- Git for obtaining the project.

The automated tests use an isolated in-memory SQLite database and do not need
access to a PostgreSQL server.

## Local development

### 1. Get the project and install dependencies

From the repository root:

```sh
git clone <your-repository-url>
cd TrackCourier
cd backend
uv sync --all-groups
```

`uv sync --all-groups` installs the locked runtime and development dependencies,
including pytest and the test client dependencies.

### 2. Set local environment variables

From `backend/`, create a root `.env` from the checked-in safe template if you
do not already have one:

```sh
cp -n .env.example ../.env
```

Edit `../.env` and set `DATABASE_URL` to a PostgreSQL database you are allowed
to use and `SESSION_SECRET` to a random value. Generate a suitable local
session secret with:

```sh
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Do not copy production credentials into a local file shared with others or
commit `.env`. The repository ignores `.env` files.

The app checks `backend/.env` first if it exists; otherwise, it reads the
workspace-root `.env`. Environment variables supplied by the shell or hosting
platform are also used by the settings system. Avoid maintaining conflicting
values in both `.env` locations.

### 3. Create an admin account

Ensure the configured database is reachable, then run the interactive setup
command from `backend/`:

```sh
uv run python -m app.cli create-admin
```

The command prompts for a username and password and then asks you to confirm
the password. Usernames must be 3–120 characters. Passwords must be 12–128
characters. Passwords are stored as Argon2 hashes; they are not accepted as
command-line arguments.

### 4. Start the development server

Still from `backend/`:

```sh
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Open:

- Public tracking page: <http://localhost:8000/>
- Admin page: <http://localhost:8000/admin.html>
- API docs: <http://localhost:8000/docs>
- OpenAPI JSON: <http://localhost:8000/openapi.json>
- Health check: <http://localhost:8000/health>

The platform start command does not enable reload. `--reload` is only for local
development.

### Optional: frontend on a separate local origin

The supported/default arrangement serves the frontend and API from one origin.
This avoids cross-origin browser requests and is the recommended deployment.
If you use a separate local static-file server, allow its exact origin in
`CORS_ORIGINS` and ensure the frontend API client is configured to call the API
origin. Merely adding a CORS origin does not change the API client's
same-origin base URL.

## Configuration and secrets

The settings are defined and validated in `backend/app/config.py`. Configure
them in the hosting provider's environment-variable/secret settings for
production; use `.env` only for local development.

| Variable | Required | Default / expected value | Purpose |
| --- | --- | --- | --- |
| `DATABASE_URL` | Yes | No default | SQLAlchemy database connection URL. Production should use PostgreSQL with provider-required TLS options. |
| `SESSION_SECRET` | Yes | No default | Secret used to sign admin session cookies. Must be at least 32 characters. Keep it stable across deploys. |
| `CORS_ORIGINS` | No | `http://localhost:5500,http://127.0.0.1:5500` | Comma-separated explicit HTTP(S) origins. Wildcard origins are rejected. |
| `SESSION_COOKIE_SECURE` | No | `false` | Set to `true` when serving production over HTTPS. Production settings reject `false`. |
| `SESSION_MAX_AGE_SECONDS` | No | `28800` | Session cookie lifetime. Allowed range is 300–2,592,000 seconds. |
| `ENVIRONMENT` | No | `development` | One of `development`, `production`, or `test`. Set to `production` on the live service. |
| `PORT` | Hosting platform | Supplied by host | Port for the ASGI server. The production command uses this value. |

For production, set `ENVIRONMENT=production`, `SESSION_COOKIE_SECURE=true`, and
`CORS_ORIGINS` to the exact HTTPS origin(s) for the frontend. Do not include
paths or use `*`. If frontend and backend share an origin, use that origin,
including the scheme and host (and port if nonstandard).

Generate a new secret instead of reusing the example value:

```sh
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Changing `SESSION_SECRET` invalidates existing admin sessions. Never place
database URLs, passwords, tokens, private keys, or real secrets in source code,
the README, or `.env.example`.

## Application behavior

### Frontend and static files

FastAPI serves `frontend/index.html` at `/` and serves the rest of the static
frontend files (including `admin.html`, CSS, and JavaScript). Static files are
part of the repository and are deployed with the service. There is no separate
frontend build step.

### Database initialization

At application startup, SQLAlchemy's `create_all` creates database tables that
do not yet exist. It does not modify existing columns or migrate an existing
schema. It does not intentionally drop tables or shipment rows. Before
changing a live schema, take a database backup and apply an explicit, reviewed
migration.

### Shipment statuses

The API validates these status values:

- `Booked`
- `Picked Up`
- `In Transit`
- `Out for Delivery`
- `Delivered`
- `Exception`

### Session behavior

Admin login uses a signed, HTTP-only cookie named `sbc_admin_session`. The
cookie uses `SameSite=Lax`; in production, it must also be marked secure and
served over HTTPS. Admin authentication is required for admin shipment
operations.

## API reference

Interactive request/response documentation is available at `/docs` while the
application is running. The API includes:

| Method | Path | Access | Description |
| --- | --- | --- | --- |
| `GET` | `/health` | Public | Lightweight process health check; does not test database connectivity. |
| `GET` | `/api/tracking/{tracking_id}` | Public | Return public shipment status and tracking history. |
| `POST` | `/api/auth/login` | Public | Authenticate an admin and set the session cookie. |
| `GET` | `/api/auth/me` | Admin session | Return the currently authenticated admin. |
| `POST` | `/api/auth/logout` | Admin session | Clear the current admin session. |
| `GET` | `/api/admin/shipments` | Admin session | List shipments. |
| `POST` | `/api/admin/shipments` | Admin session | Create a shipment and its initial tracking event. |
| `GET` | `/api/admin/shipments/{shipment_id}` | Admin session | Get a shipment and its details. |
| `PUT` | `/api/admin/shipments/{shipment_id}` | Admin session | Update shipment fields. |
| `POST` | `/api/admin/shipments/{shipment_id}/events` | Admin session | Add a tracking event and update the current status. |
| `DELETE` | `/api/admin/shipments/{shipment_id}` | Admin session | Delete a shipment and its associated tracking events. |

API request bodies and response schemas are described in `/docs`. Inputs are
validated; for example, tracking IDs must not be empty and are limited to 100
characters. A tracking ID must be unique. Deleting a shipment is destructive
and removes its associated event history.

Example public tracking request:

```sh
curl -i http://localhost:8000/api/tracking/EXAMPLE-TRACKING-ID
```

Example admin login request (replace the example username/password locally;
never put a real password in a committed script):

```sh
curl -i -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"username":"operator","password":"replace-this-locally"}' \
  http://localhost:8000/api/auth/login
```

Use the cookie jar for subsequent admin calls:

```sh
curl -i -b cookies.txt http://localhost:8000/api/auth/me
```

Remove the local cookie file when finished. Do not use real credentials in
shell history on a shared machine.

## Testing

Run tests from `backend/`:

```sh
uv run pytest -c pyproject.toml ../tests
```

The tests set test-only environment variables and use an isolated in-memory
SQLite database. They do not connect to the configured production database.
The test suite covers authentication, admin shipment operations, and public
tracking behavior.

## Production deployment

The repository contains a Render Blueprint in `render.yaml`. It defines one
Python web service so the same process can serve the frontend and API.
Deployment to another Python hosting service is also possible if it supports
the equivalent commands, environment variables, public HTTPS, and health
checks.

### Render via Blueprint

1. Push this repository to GitHub.
2. In Render, create a new **Blueprint** and choose the repository. Render
   reads `render.yaml` and proposes the `trackcourier` web service.
3. Provision or select a production PostgreSQL database. Set `DATABASE_URL` to
   its connection URL, including any TLS/SSL parameters required by that
   provider.
4. Let Render generate `SESSION_SECRET`. Do not regenerate it for routine
   deploys; keep the secret persistent.
5. Set `CORS_ORIGINS` to the service's exact HTTPS origin. Once a custom domain
   is attached, include that HTTPS origin too. Separate origins are
   comma-separated.
6. Confirm `ENVIRONMENT=production` and `SESSION_COOKIE_SECURE=true`.
7. Create the service and wait for its first deploy to finish.
8. Use a one-off interactive shell/command in the deployed service to create
   the first administrator (instructions below).
9. Verify the service URL, health endpoint, frontend, API docs, and an actual
   database-backed tracking/admin flow.

The service root is the repository root. The Blueprint build and start
commands run inside `backend/`.

**Build Command**

```sh
pip install uv && cd backend && uv sync --no-dev --frozen
```

**Start Command**

```sh
cd backend && uv run --no-sync uvicorn app.main:app --host 0.0.0.0 --port $PORT
```

Configure the health-check path as `/health`. The start command binds to
`0.0.0.0` and uses the platform's `PORT`. Do not use `--reload` in production.
The app serves the frontend itself, so no separate frontend service or build
is needed for the standard setup.

### Required production environment

| Variable | Production configuration |
| --- | --- |
| `DATABASE_URL` | Valid production PostgreSQL connection URL; protect as a secret and use TLS. |
| `SESSION_SECRET` | Persistent random secret, minimum 32 characters. |
| `CORS_ORIGINS` | Exact HTTPS origin(s) serving the frontend. No `*`, URL paths, or trailing paths. |
| `ENVIRONMENT` | `production`. |
| `SESSION_COOKIE_SECURE` | `true`. |
| `SESSION_MAX_AGE_SECONDS` | Optional; default is 28800 seconds (8 hours). |
| `PORT` | Supplied by the hosting provider; do not hard-code it in the deployed command. |

The runtime requires `DATABASE_URL` and `SESSION_SECRET`; startup fails if they
are missing or invalid. Keep secrets in the hosting platform's secret manager,
not in GitHub repository files or build logs.

### Create the first production admin

After the first deployment, open the hosting provider's one-off shell or
interactive command facility. Run this from `backend/`:

```sh
uv run --no-sync python -m app.cli create-admin
```

Enter the username and password at the prompts. This requires database
connectivity. Do not add admin credentials to the build command, start command,
repository, or environment variables.

### Connect a custom domain and HTTPS

1. Add the desired domain in the web service's custom-domain settings.
2. Copy the DNS records provided by the hosting platform into the domain's DNS
   provider exactly as instructed. Remove conflicting records only when the
   platform directs you to.
3. Wait for DNS verification and TLS/HTTPS certificate provisioning.
4. Test the custom domain using `https://`; production admin cookies require
   HTTPS.
5. Add the custom domain's exact HTTPS origin to `CORS_ORIGINS` and restart or
   redeploy if the platform requires it.
6. Confirm the public page, static assets, admin login, session persistence,
   and API calls all work under the custom domain.

Do not hard-code a domain in the application. The app does not automatically
configure DNS or issue a TLS certificate; those steps are handled by the
hosting platform and DNS provider.

### Other hosting providers

For Railway or another Python web host, configure the repository root, install
`uv`, sync dependencies from `backend/`, run the same Uvicorn command, and set
the environment variables above. Configure the health check to `/health`,
provide PostgreSQL, and enable HTTPS/custom-domain support with the provider.
The exact dashboard labels and DNS records vary by host; follow the provider's
current instructions.

## Database, backups, and file storage

- PostgreSQL is the intended production database. Set `DATABASE_URL` to the
  managed database's connection string; do not rely on ephemeral local
  SQLite for production shipment or admin data.
- Use the database provider's automated backups and retention options. Test
  restoring a backup before relying on production data.
- Startup creates missing tables but does not migrate existing tables. Plan
  and apply reviewed schema migrations before deploying model changes that
  affect existing data.
- There are no user-uploaded files or app-generated persistent documents in
  the current application. Frontend files are static repository assets.
- Application instances should be treated as replaceable. Do not store
  important data on a hosting provider's ephemeral application filesystem.

## Security and operations

- Do not commit `.env`, database credentials, secrets, admin passwords, or
  session cookies. The root `.gitignore` excludes `.env` and virtual
  environments.
- Use a distinct strong `SESSION_SECRET` in production and keep it stable
  between releases. Rotating it signs users out.
- Keep `SESSION_COOKIE_SECURE=true` and serve the app only over HTTPS in
  production.
- `CORS_ORIGINS` must contain explicit allowed origins. The application
  rejects wildcard origins.
- Admin routes require an authenticated session. Passwords are hashed using
  Argon2.
- `/health` only indicates that the web process responds. It does not prove
  database availability; monitor the app and database separately.
- There is no application-level rate limiter. Use platform or trusted
  reverse-proxy request controls, particularly for login and public tracking.
- The application logs unhandled API exceptions, but this project does not
  currently configure a third-party error-reporting service or alerting.
- `create_all` is not a migration system. Back up the database and use
  explicit migrations for schema changes.

## Troubleshooting

### The app fails during startup

Check deploy logs. Verify that `DATABASE_URL` and `SESSION_SECRET` are present,
the database permits connections from the hosting service, the database URL
uses the provider's expected TLS settings, and the start command points to
`app.main:app` from `backend/`.

### The host reports that the health check failed

Set the health-check path to `/health`. Confirm that Uvicorn binds to
`0.0.0.0` and uses `$PORT`. The health endpoint does not check database
connectivity, so database-backed API failures require checking the database
connection and application logs separately.

### The page loads but styles or scripts do not

Deploy from the repository root and make sure the `frontend/` directory is
included in the build. The app serves files at paths such as `/css/style.css`
and `/js/tracking.js`.

### Browser requests fail with a CORS error

The standard setup serves API and frontend from the same origin and does not
need cross-origin requests. If using different origins, set `CORS_ORIGINS` to
the exact frontend origin. The frontend client defaults to the deployed Render
API origin; for a different backend host, add
`<meta name="api-base-url" content="https://api.example.com">` to both
frontend HTML pages. Check the browser console and network requests.

### Admin login works but subsequent requests appear logged out

Use HTTPS in production, keep `SESSION_SECRET` unchanged across releases, and
check that the browser accepts cookies. For cross-origin frontends, check
cookie and CORS configuration as well as the allowed origin.

### Shipment or admin operations fail after a model change

The automatic table creation step does not update existing columns. Apply the
required database migration after taking a verified backup; do not expect a
normal app restart to change an existing schema.
